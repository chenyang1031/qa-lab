# Day 17 · 区分应用、数据库与压测工具的 CPU 开销

日期：2026-11-27（UTC+8）

## 一、学习目标与单位

分别读取 K8s 容器指标和 JMeter 进程指标，避免把节点总 CPU 上升全部归因于商城。

- kubectl top 的 1000m = 1 个 CPU 核心；1481m = 约 1.481 个核心。
- top 默认进程 CPU 显示口径中，100% = 1 个逻辑 CPU 的计算量；36% = 约 0.36 个核心。
- 节点总体 CPU 百分比通常按全部逻辑 CPU 归一化，不能直接与单核口径相加。比如 8 个逻辑 CPU 时，0.36 核约占整机总计算量的 4.5%。

## 二、实验 A：K8s 容器采样 + 商品列表压测

配置：20 线程，ramp-up 10 秒，计划时长 60 秒，GET http://127.0.0.1:8002/products。
JMeter 测试约 16:21:48–16:22:50。

| 组件 | 压测前 CPU | 记录内最高 CPU | 内存 |
|---|---|---|---|
| app | 约 3m | 1481m | 约 58–61Mi |
| mysql | 约 16–52m | 236m | 约 499–500Mi |
| redis | 约 5–8m | 8m | 约 5–6Mi |

请求总数 5933，JMeter 记录失败数 0；汇总吞吐量 95.8 次/秒，平均响应约 165ms（JTL 分析输出），P95 265ms。

观察：本轮记录中 app CPU 增幅明显大于数据库，Redis 变化较小。CPU 开销更高不等于已经证明它是性能瓶颈。

采样延迟：连续几次 kubectl top 返回相同数值；查询间隔不是指标更新间隔，CPU 也代表统计窗口平均值。16:23:07 仍显示 1481m，不能据此断定压测后 CPU 一直居高不下。补查到统计时刻 16:24:06 的 app CPU 已回落至约 3m。

## 三、实验 B：重复相同压测，补采 JMeter 进程 CPU

- 结果目录：sandbox/load/day17_jmeter_20261127_162721/
- CPU 日志：sandbox/load/day17_jmeter_cpu_20261127_162822.log
- JMeter PID：3454，通过 ApacheJMeter.jar 命令行匹配确定。
- JTL 实际请求区间：16:27:33.501–16:28:35.386。
- 请求总数 5320，失败数 0，响应码均为 HTTP 200。
- JMeter 汇总吞吐量 85.1 次/秒、平均 RT 192ms；原始 JTL 平均约 193ms，P95 351ms。

| 采样时刻 | JMeter 进程 CPU | 说明 |
|---|---|---|
| 16:28:22 | 12.5% | 第一帧不作为此前固定 2 秒区间的采样依据 |
| 16:28:24 | 36.0% | 约 0.36 核 |
| 16:28:26 | 14.0% | 约 0.14 核 |
| 16:28:28 | 21.5% | 约 0.215 核 |
| 16:28:30 | 18.4% | 约 0.184 核 |
| 16:28:32 | 35.5% | 约 0.355 核 |

第 2–6 帧均落在压测请求区间内；只能代表这约 10 秒的采样，不是整轮平均或整轮最大值。

top 的 java 行是所选 JMeter 进程，%Cpu(s) 行是系统总体 CPU；两行的分母不同。
同一帧中系统 id=57.6% 意味着总体忙碌约 42.4%，不能直接减去 java 的 36% 当成服务开销。

## 四、今天能报告的结论与边界

1. 商城应用、MySQL、JMeter 都产生了可测的 CPU 开销；本次所采 Redis CPU 较低。
2. 两轮性能结果有波动，未实施调优，不能把波动称为优化收益。
3. 实验 A 的容器数据与实验 B 的 JMeter 数据不是同轮、也不是相同窗口，不能直接相加或计算各组件占比。
4. 当前证据没有证明 JMeter 达到极限，也没有证明 app 已是瓶颈。
5. 下一步若要定量归因，需要在同一轮、同一时间窗口采集各项指标，统一 CPU 单位，并结合吞吐、响应时间、资源限制和排队证据。独立压测机可减少同机资源竞争。
6. HTTP 200 与 JMeter 错误率 0 还不能代替响应内容业务断言。
