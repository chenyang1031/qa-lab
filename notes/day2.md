# Day 2 · Redis 动手:用测试的眼睛玩缓存

> 当天目标:60 分钟,六个实验,建立"作为测试如何验证缓存"的基本功。

## 容器

```bash
docker run -d --name redis7 -p 6379:6379 redis:7    # 首次拉镜像较慢
docker exec -it redis7 redis-cli                     # 提示符变成 127.0.0.1:6379>
```

`-p 6379:6379` = 把容器的 6379 端口映射到本机 6379。本机还有个旧容器 redis-easytest 也占 6379(处于停止态),两者不能同时启动。

## 六个实验(命令 + 结论)

| # | 命令 | 结论 |
|---|---|---|
| 1 | `SET name chenyang` / `GET name` | 缓存操作的最小原子:写和读 |
| 2 | `SET captcha abc123 EX 60` → `TTL captcha` | EX 60 = 60 秒自动删除;TTL 返回剩余秒数且在倒数。"验证码 60 秒有效"后端就这么实现 |
| 3 | `TTL` 三种返回 | **-1 = key 存在但永不过期("永生");-2 = key 不存在("死了");正数 = 剩余倒计时** |
| 4 | `SET login:chenyang token EX 1800` → `DEL` → `GET` 变 (nil) | "会话过期""退出登录"的后端实现:DEL 或等 EX 到期 |
| 5 | `SET pv 0` → `INCR pv` × 3 → `GET pv` = 3 | INCR 原子自增:限流、计数的原型;并发下 INCR 准确性 = 第 12 周"重复提交"测试的种子 |
| 6 | `INFO stats` 找 keyspace_hits / keyspace_misses | 命中率 = hits ÷ (hits + misses),压测时看的核心指标 |

**批改记录**:实验 3 最初把 -1 理解成"过期",已纠正。记忆法:-2 死了(不存在)、-1 永生(不过期)。"改了数据、页面不更新"类 bug 排查第一件事就是 `TTL` 一下:看到 -1,缓存未失效就是罪证。

## 测试视角三问(批改后定稿)

**1. 怎么验证缓存生效?**
- 现象层:同一查询连发两次,第二次响应明显更快
- 数据层:redis-cli 能 `GET` 到后端写入的 key;`INFO stats` 的 hits 在涨

**2. 怎么验证过期时间?**
- 操作后立刻 `TTL key`,剩余秒数符合需求(说 1800 就是 1800 左右)
- 等到期后 `GET` 返回 nil
- **边界**:到期前一秒操作一次,看被续期还是被踢——一半的过期 bug 在边界上

**3. 命中率低说明什么?**
三种可能,逐个排查:
- 缓存根本没被用上(代码没走缓存逻辑 / Redis 挂了)
- key 设计不合理(过期太短、被误删)
- 查询全是冷数据
后果:流量全打数据库,数据库 CPU 飙升、接口变慢。

## 面试可用的一句话

"改了数据库、页面不生效"的 bug 十有八九是缓存没失效。提单时写"疑似缓存未失效,建议检查缓存更新策略",研发会觉得你很懂。
