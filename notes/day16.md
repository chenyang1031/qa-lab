## 二、组件与查询

node-exporter 提供节点指标 → Prometheus 定时采集并保存 → Grafana 查询并展示。

CPU 使用率（最近 1 分钟平均）：

```promql
100 * (1 - avg by (instance) (
  rate(node_cpu_seconds_total{mode="idle"}[1m])
))
```

内存使用率：

```promql
100 * (1 - node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes)
```

两个面板都选择 Percent (0-100)，坐标范围 0 到 100。
这些是 node-exporter 所见节点的指标，不是单个应用容器的指标。

## 四、时间对齐后的资源观察

Grafana 使用绝对时间 15:51:00 至 15:56:00。
以下百分比是截图目测近似值，不是导出指标的精确统计。

| 阶段 | CPU | 内存 |
|---|---|---|
| 压测前 | 约 13%–25% | 约 30% |
| 压测期间及 1 分钟平滑窗口内 | 升至约 50%–51% | 升至约 32% |
| 压测结束后的观察窗口 | 回落至约 20%–30% | 约 30%–32% |

CPU 图的峰值约在 15:53:30，略晚于最后一个请求完成，与 1 分钟 rate 统计窗口的平滑/滞后相符。
约 15:48 的更高 CPU 峰早于这次实验，不能归因于本次压测。

可报告的结论：本轮请求均为 HTTP 200；压测时间附近节点 CPU 上升并在结束后回落，内存短时小幅波动。
边界：单轮短测不足以确认容量上限、具体瓶颈或内存泄漏。JMeter 与被测服务在同一台电脑，节点指标也包含其他负载，需要应用/数据库各自指标与重复对照进一步定位。

## 五、踩坑与修正

1. No data：最初查询了旧的固定时间段。调整到有采样数据的时间后出现折线；没有数据不等于 CPU 为 0。
2. 看板与图表混淆：CPU、内存曾分别放在两张 Dashboard；后来把两个 Panel 放到 qa-lab 性能监控中。
3. 时间对齐：先确认 JTL 请求起止时刻，再解读曲线，不能把之前的峰值当成本次结果。
4. 吞吐量口径：分析脚本用首末请求开始时间之差 57.054 秒，得到约 91.0 次/秒；用首个开始到最后完成 57.274 秒得到约 90.6 次/秒；JMeter 汇总约 60.4 秒得到约 85.9 次/秒。对比实验必须保持口径一致。分析脚本尚未修改。
